# AGENTS.md — інструкції для AI-агентів

Сайт робототехнічної команди «97 Ом» ліцею №97 (Дніпро): https://97ohmrobotics.github.io.
Репозиторій ведуть наставники й учні через pull request.

Цей файл — єдине джерело правил для агентів (Claude Code, Codex, Cursor тощо); `CLAUDE.md` лише підключає його.
Дизайн — у [THEME.md](THEME.md), інструкція для людей — у [CONTRIBUTING.md](CONTRIBUTING.md).
Якщо в PR змінюються правила, схема контенту чи домовленості, онови цей файл у тому ж PR.

## Головне

1. Ніколи не пушити в `main`. Тільки гілка → pull request → зелена перевірка **Check** → злиття людиною.
2. Перед кожним PR `npm run build` має пройти без помилок.
3. **Фото, де є люди** (навіть спиною чи тільки руки), ніколи не додавати в репозиторій. Тільки посилання з Cloudinary команди.
4. Обличчя учнів не публікуємо, доки немає письмової згоди батьків. Учні на сайті — тільки «Ім’я П.».
5. Не пиши опис до зображення, якого не бачив. Не можеш відкрити — попроси людину надіслати його в чат.
6. Не вигадуй фактів: результатів, дат, імен, цифр, цитат, посилань. Чого бракує — питай.
7. Сайт українською. Назва в тексті — «97 Ом» або 97 Ohm Robotics. Знак Ω — тільки в логотипі.
8. Один PR — одна зміна: новина, учасник, правка дизайну.
9. Агент не зливає PR сам, навіть якщо має права, — лише коли людина прямо про це попросила.
10. Жодних секретів і ключів у репозиторії (cloud name `lyceum97media` — не секрет).

## З ким працюєш

- Зазвичай з тобою працює наставник (Сергій або Максим), іноді учень. Відповідай мовою повідомлення людини, а текст для сайту пиши українською.
- Сайт публічний, учні неповнолітні. Сумніваєшся щодо приватності, факту чи формулювання — спитай.
- Мережа агента може не пускати на `res.cloudinary.com` і `97ohmrobotics.github.io` (так буває в Claude Code у браузері).
  Тоді не вгадуй: попроси людину прикріпити зображення в чат, а стан сайту перевір через запуски в Actions.

## Стек і команди

- Astro 7, контент — Markdown з frontmatter, схеми полів — Zod у `src/content.config.ts`. Звичайний CSS, без Tailwind і без CMS.
- Node.js 24 (`.nvmrc`). TypeScript закріплено на `^6`: `astro check` ще не підтримує TS 7, не оновлювати.
- Markdown обробляє Sätteri (стандарт Astro 7). Плагіни підключаються через
  `markdown.processor: satteri({ hastPlugins: [...] })` в `astro.config.mjs` (приклад — `src/lib/cloudinary-markdown.ts`),
  а не через `markdown.rehypePlugins`: той вимагає `@astrojs/markdown-remark`, якого в проєкті немає.

```sh
npm ci
npm run dev                  # http://localhost:4321, чернетки (draft: true) теж видно
npm run build                # astro check (типи й схеми) + astro build — те саме, що Check на PR
SHOW_DRAFTS=1 npm run build  # зібрати разом із чернетками
```

Публікація: після злиття в `main` workflow **Deploy to GitHub Pages** за 1–2 хвилини оновлює сайт.
Ще він сам запускається щопонеділка о 03:00 UTC (05:00–06:00 за Києвом), щоб минулі анонси змагань зникали з головної.

## Як вносити зміни

1. Свіжа гілка від актуального `main`, назва за змістом: `journal/2026-11-15-robotour-kyiv`, `fix/join-schedule`.
   Якщо середовище саме задає назву гілки (як Claude Code у браузері), використовуй її.
2. Зміни → `npm run build` → коміт.
3. Коміт українською, коротко: «Розділ: що зроблено». Приклади з історії:
   «Журнал: обкладинка допису такої ж ширини, як текст», «Команда: наставник Максим і 10 учасників».
4. PR: заголовок як у коміта, тіло за шаблоном `.github/pull_request_template.md` (розділи «Що змінено» і «Перевірка»).
   Чекбокси відмічай чесно; що не перевірив — так і напиши.
5. Попроси переглянути PR іншого наставника (Сергій — `serhii-teacher`). Схвалити власний PR автор не може.
6. Червоний Check: відкрий лог, знайди причину, виправ і запуш у ту саму гілку. Не вимикай перевірки й не обходь схему.
7. Після злиття переконайся, що Deploy пройшов (вкладка Actions).

Файли `example-*.md` з `draft: true` — демо-приклади, на сайт не потрапляють.

## Журнал (найчастіше завдання)

Файл: `src/content/journal/uk/РРРР-ММ-ДД-два-три-слова.md` — дата події й кілька слів латиницею, малими, через дефіс.
Після публікації назву файлу не міняти: зламається адреса.

```markdown
---
title: "Robotour Kyiv: 4-те місце і перегрітий драйвер"
date: 2026-11-15
type: competition
project: line-follower-2026  # id існуючого проєкту
result: "4 місце з 18"
cover: https://res.cloudinary.com/lyceum97media/image/upload/v1792951743/field.jpg
cover_alt: "Поле змагань із чорною лінією, команда спиною до камери"
authors: [serhii]            # id існуючих файлів з members/uk/
tags: [robotour, змагання]
---

Перший абзац — одне-два речення, зрозумілі без решти тексту.

## Що спрацювало
...
```

| Поле | Обов’язкове | Що писати |
|---|---|---|
| `title` | так | від 3 символів; конкретно, без капсу |
| `date` | так | `РРРР-ММ-ДД`, дата події |
| `type` | так | `news` — новина, `competition` — змагання, `devlog` — нотатки розробки |
| `project` | ні | `id` проєкту (назва файлу з `projects/uk/` без `.md`) |
| `result` | ні | тільки для `competition`: «4 місце з 18» |
| `cover`, `cover_alt` | ні, але разом | обкладинка 21:9 і її опис (див. «Зображення») |
| `authors` | ні | `id` з `members/uk/`: наставники — `serhii`, `maksym` |
| `tags` | ні | кілька слів |
| `draft` | ні | `true` — чернетка, на сайт не потрапляє |

Як писати:
- `project` і `authors` мають посилатися на файли, що існують, інакше збірка впаде з «Invalid content reference».
- **Перший абзац** — короткий підсумок. Він показується у списку журналу й стає описом сторінки для пошуковиків (перші ~160 символів).
- Далі: що робили, що спрацювало, що ні, що змінимо. Факти й цифри, від «ми», без пафосу.
- Текст, який дала людина, не переписуй по суті: виправ помилки й типографіку, а більші зміни запропонуй.
- Підзаголовки — `##` (заголовок сторінки — це `title`). Учнів згадувати як «Олена К.».
- **Анонс змагання:** `type: competition`, дата в майбутньому, без `result` — з’явиться на головній як «Найближче змагання».
  Після змагань допиши `result` і звіт **у той самий файл**, нового не створюй.

## Проєкти, учасники, сторінки

Повні шаблони — у CONTRIBUTING.md. Що перевіряє збірка і що легко пропустити:

- **Проєкт** (`projects/uk/`): `status` — `idea | in-progress | done | retired`; для `done` обов’язкова дата `finished`;
  `summary` до 200 символів (порожній → перший абзац). Розділ `## Що не вийшло` обов’язковий для всіх, крім `idea`, — без нього збірка падає.
  Назву пиши як тип і ім’я робота в лапках: Лінійний трекер «Ворон». На головній і в журналі сайт показує саме частину в лапках.
  Номери P-01, P-02… ставляться самі за датою `started`.
- **Учасник** (`members/uk/`, файл `olena-k.md`): `name` — ім’я й перша літера прізвища, «Олена К.» (повне прізвище схема не пропустить);
  `role` — `капітан | механіка | електроніка | програмування | маркетинг | наставник`, один або список, перший — головний;
  `title` — необов’язковий підпис ролі до 60 символів («тімлід»); `joined` — рік; `grade` — клас;
  `avatar` — **порожньо**, доки немає згоди батьків (тоді показуються ініціали); `active: false` — випускник.
- **Головна** (`pages/uk/home.md`): `hero` — фото 4:3; `hero_alt` водночас опис і видимий підпис «РИС. 1 — …».
- **Приєднатися** (`pages/uk/join.md`): `schedule`, `place`, `telegram` (повне посилання `https://t.me/...`), `email`, `address`.
  Порожні поля не показуються. Текст під frontmatter — блок «Батькам і партнерам».

## Зображення

| Що на фото | Де зберігати | Як вказати |
|---|---|---|
| Без людей: робот, плата, схема, поле | репозиторій: `public/media/<розділ>/<id-запису>/` | `/media/journal/2026-11-15-robotour-kyiv/field.jpg` |
| **Є люди** — навіть спиною чи тільки руки | Cloudinary команди, cloud name `lyceum97media`; завантажує наставник | посилання з кнопки **Copy URL**, без змін |

Чому так: git і навіть закриті PR зберігають файли назавжди, тож фото з дітьми з GitHub уже не видалити. З Cloudinary — можна.

**Cloudinary**
- Посилання вигляду `https://res.cloudinary.com/lyceum97media/image/upload/v1792947166/hero-image.jpg`, формати jpg, png, webp, avif, heic.
  Бери його тільки від людини: збірка не перевіряє, чи файл існує, тож вигадане посилання дасть биту картинку.
- Нічого не дописувати: ні перетворень (`w_800`, `c_fill`…), ні параметрів. Сайт сам підставляє розмір, WebP/AVIF і `srcset`.
  Посилання з будь-якого іншого сайту (або з іншого cloud name) схема відхилить.
- Папки повторюють сайт: `home/`, `journal/<id-допису>/`, `projects/<id-проєкту>/`, `team/`. Перенесення між папками посилання не змінює.
- Перед завантаженням дай файлу унікальну назву латиницею (`2026-11-15-robotour-field.jpg`): назва стає частиною посилання,
  і два різні `cover.jpg` легко сплутати чи перезаписати.
- EXIF (зокрема GPS) треба стерти **до** завантаження: squoosh.app або `exiftool -all= фото.jpg`.
  Сайт віддає фото без EXIF, але оригінал за «голим» посиланням його зберігає.

**Репозиторій**
- Формати jpg, png, webp, avif, svg; до 2000 px по довгій стороні, бажано до ~500 КБ.
- Ці файли сайт віддає як є, без стиснення й без очищення: EXIF стирати обов’язково.

**Опис (`cover_alt`, `hero_alt`, `![опис](...)`)**
- Обов’язковий і **описує, що на зображенні**, для людей, які його не бачать. Не гасло й не підпис-емоція.
  Добре: «Робот на чорній лінії, вид згори». Погано: «Ми готові до нових викликів!»
- Згенероване ШІ зображення починай з «Ілюстрація: …» і не видавай за фото команди.
- Перед використанням будь-якого зображення перевір: немає облич, імен, бейджів, номерів, особистих даних на екранах.

**Пропорції** (`object-fit: cover`, зайве обрізається по центру): обкладинка допису й проєкту — 21:9,
фото першого екрана — 4:3, картка проєкту й мініатюра в журналі — 3:2.
Фото в тексті: `![опис](посилання)` — для Cloudinary сайт теж додасть `srcset`.

## Приватність

- Не публікувати без письмової згоди батьків: обличчя учнів, портрети.
- Ніколи не публікувати: повні прізвища учнів, класи й номери на одязі, бейджі з іменами, телефони, адреси, особисті акаунти, геомітки.
- Обличчя потрапило в кадр — не бери фото, попроси людину обрізати або замінити.
- Усе, що хоч раз потрапило в PR, лишається в історії GitHub назавжди. Сумнівне не додавай навіть «тимчасово».

## Мова й типографіка

- Назва: укр. «97 Ом» (робототехнічна команда «97 Ом»), англ. 97 Ohm Robotics, коротко 97 Ohm. Адреса й хендли — `97ohmrobotics`.
  Знак Ω — тільки в логотипі й на мерчі; читається «Ом», не «омега».
- Тон: спокійний, інженерний, від «ми». Без пафосу, гучних епітетів і обіцянок; про невдачі — чесно.
- Лапки «ялинки», апостроф ’, тире — з пробілами, десяткова кома (7,4 В; у полях `hardware` можна як у даташиті). Дати в тексті словами: 15 листопада.
- Змішані алфавіти (латинська «O» в «97 Ом») ламають пошук. Перевірка — має бути порожньо:
  `rg -n '\p{Latin}\p{Cyrillic}|\p{Cyrillic}\p{Latin}' src/content` (у Claude Code — інструмент Grep з тим самим шаблоном).

## Код і дизайн

- Перед будь-якою зміною вигляду прочитай [THEME.md](THEME.md).
- Кольори — тільки через CSS-змінні. Темна тема в `global.css` записана двічі (ручний вибір і «авто») — міняєш одне, міняй обидва.
- Стилі сторінки чи компонента — у `<style>` цього `.astro`-файлу; спільне — у `global.css`. Спершу шукай готовий клас.
- Перевіряй на ширині 390 px і 1280 px, у світлій і темній темі. До PR зі зміною вигляду додавай знімки екрана.
- Змінив схему контенту — онови CONTRIBUTING.md, шаблони й цей файл у тому ж PR.
- Коментарі в коді — українською, коротко, як у сусідніх файлах.

## Чого не робити без прямого прохання

- Переписувати історію: `push --force`, rebase спільних гілок.
- Міняти `public/brand/`, workflows у `.github/`, залежності в `package.json`.
- Видаляти чи переписувати чужі дописи й картки учасників.
